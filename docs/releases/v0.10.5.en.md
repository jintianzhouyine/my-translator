Restore system audio after calls, independently control original and translated audio, and remember the selected engine.

## Changes

- Added “Audio sent to the other party” controls at the upper right of the live translation page: original and translated audio can be toggled independently, with separate 0–100% volume controls and automatically saved preferences.
- Original audio comes from the physical microphone and is mixed locally with Qwen translated speech before being sent to the virtual microphone. Original audio is off by default; translated audio is on. Muting clears that channel's queued audio so old speech is not replayed when re-enabled.
- Starting a duplex call records the system's default microphone and playback device, then sets the virtual microphone as the default system input. Pause, stop, failed startup and normal exit restore the original devices.
- Retain recovery records after abnormal exits and attempt to repair system defaults on the next startup. Handle disconnected devices, asynchronous switch timeouts and cancellation during startup.
- Remember the selected engine and open the main interface directly when already configured. The first-run selector closes only after saving successfully, allowing retries after a save failure.
- Fixed concurrent saves of volume, engine and other settings potentially overwriting one another. Settings edited during a session use its already locked physical audio devices.

## Usage notes

Automatic switching supports BlackHole on macOS and standard-name VB-CABLE devices on Windows (including A/B/C/D). A meeting application can receive audio through its system-default microphone. Use headphones for playback. For other virtual devices, turn off “Set as the system default microphone during calls” and configure routing manually.

If you previously changed system defaults to a virtual device manually, explicitly select a physical microphone and “Meeting playback / recovery device” in the translator as the recovery targets. After a forced process termination, recovery can only be attempted at the next startup.

When original and translated audio are both enabled, delayed translations may overlap with the original speech. Disabling translated audio affects output only; recognition, captions and cloud sessions continue.

## Installers

This Release starts as a draft. After a manual build is triggered, the workflow uploads installers and publishes only after tests, packaging and architecture checks pass on both platforms:

- **Apple Silicon Mac**: `MyTranslator_0.10.5_aarch64.dmg`.
- **Windows x64 (Intel/AMD 64-bit)**: `MyTranslator_0.10.5_x64-setup.exe`.
- `SHA256SUMS`: installer checksums.

To trigger the build, select `main` in **Build & Release** and enter tag `v0.10.5`. Creating a draft and pushing a tag do not automatically trigger builds.

## Validation scope

282 local JavaScript tests and 48 macOS Rust tests passed. The Windows system-device module passed a compile check for the x64 GNU target. Browser previews checked the upper-right controls, minimum desktop window width and compact mode.

Windows installers and full platform builds depend on the manually triggered CI result. End-to-end calls with real cloud translation, virtual audio devices and meeting applications still require validation on target computers.

macOS uses an ad-hoc signature, without an Apple Developer signature or notarization. The Windows installer has no publisher certificate.
